3. Diagnosis
* When tracing the DNS to the destination, we must first begin with DNS searching for site.lab.example. The DNS finds it in an old A record (198.51.100.24). This is within the old Azure VM, rather than in Railway. The curl command tracks where the DNS was locted (198.51.100.24). Proof of this is within the line: Connected to site.lab.example (198.51.100.24).
* When TLS tries to reach the certificate, we are able to confirm that it is within the old VM. The only certificate that is revealed is CN=old-vm.lab.example. Since the names do not align with one another, the connection is failed.
* The evidence supports the claim that the primary problem is within the DNS. The previous Azure A record is still up. This causes site visitors to be sent to the old server. The certificate differentiation is a byproduct of this. Since the servers are not supposed to be "talking" to each other, the certificates would not match. This means that the certificates is not the main issue, but rather the DNS. Traffic headed towards the old Azure VM IP is evident in (198.51.100.24). The incorrect certificate name (old-vm.lab.example) also support this. 
* One thing that still remains uncertain is the Railway certificate. I am still unsure if it will issue the certificate correctly. I also only have one 'dig' call, which means that other answers may be cached.
